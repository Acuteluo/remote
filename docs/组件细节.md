## 组件与职责

| 组件 | 位置 | 作用 |
|---|---|---|
| meow-console | `console/server.py` + systemd 用户服务 | 门户本体: 状态面板 / Web 终端 / 远程桌面桥接 / 剪贴板 / 摄像头 / 电源 |
| meow-vnc | systemd 用户服务(x11vnc) | 只监听回环的 VNC 服务端, 由门户桥接给浏览器, **端口永不对外** |
| meow-forward | `lan_forward.py` + systemd 用户服务 | 把发往本机各网卡 IP(含 Tailscale 100.x)的端口镜像到回环 |

常用命令:

    systemctl --user status meow-console meow-vnc meow-forward
    journalctl --user -u meow-console -f
    tailscale status                     # 查看 Tailscale 设备

## 端口

默认 8390(控制台) / 5900(x11vnc), **都不是写死的**:

- 优先级: 命令行 `--port` > 环境变量 `MEOW_PORT` > `console/data/config.json` 里的 `port`
- VNC 端口同理: `--vnc-port` > `MEOW_VNC_PORT` > `config.json` 的 `vncPort`
- 换端口后 `lan_forward.py` 会自动跟着走(它读同一份 config)

## 摄像头页的开关与两个延迟读数(2026-10-23)

**开关**: 「摄像头画面」和「麦克风」是两个独立开关, 进页面**默认都关** ——
不点开关一个字节都不采, 服务端也不会起 ffmpeg。关掉 = 立刻断开(服务端一收到
WS close / HTTP 流断就 kill 采集); `pagehide` 时两个都停; 开关状态**不写
localStorage**, 所以下次进来又是关的。切后台是"暂停"(开关状态留着, 切回来接着用)。

因为拆成了两个开关, 收音不能再靠摄像头 WS 的心跳判活(只开麦、或开着收音把画面
关掉都会被误杀)。所以:

- `GET /api/audio/hb` —— 麦克风自己的"页面还开着"心跳, 5 秒一次。
  和摄像头 WS 的 `{"t":"hb"}` 写同一个 `_page_seen["t"]`(见 `server.py`)。
  顺手把服务端采集管道自身的滞后捎回去, 省掉一次单独轮询。
- 前端开麦时会立刻先发一次这个心跳; 服务端在 `_serve_audio` 的循环里**再判一次**
  `tied`, 所以不要求"心跳一定先于开流到达"(那会把用户手势链拉长, `play()` 可能
  被自动播放策略拦掉)。

**两个延迟读数**(都是**在手机上**算的, 网络那一段天然算在内):

| 读数 | 怎么算 | 精度 |
|---|---|---|
| 画面 X 前 | 服务端每帧先发 `{"t":"f","s":<服务端毫秒>}`, 前端用 `/api/time` 对齐时钟后算 `本机现在 + 偏移 - s` | ±RTT/2 |
| 声音 X 前 | 服务端按 sid 记下"这条流**第 0 个采样**是什么时候采到的"(`audioSince`), 前端算 `(本机现在 + 偏移) - (audioSince + currentTime*1000)` | 见下 |

**声音这条为什么不用 `buffered`**: 一开始是用浏览器的
`buffered.end - currentTime`(还有多少没播)去估的。但 `buffered` 是**粗粒度更新**的
(隔一段才刷一次), 算出来是锯齿状乱跳(实测 0.1~3.6s), 根本不能当读数 ——
而服务端那条管道其实非常平滑(实测交付间隔中位 91ms、最大 102ms)。
改成服务端给锚点之后读数就稳了(实测 5.54 → 5.72 → 5.75s)。

**验证方法**(可复现): 起一个能给 TCP 加固定单向延时的中继, 让浏览器走它:

| 场景 | RTT | 画面 | 声音 |
|---|---|---|---|
| 直连 | 1ms | 1ms | 5700ms |
| 中继 D=0 | 1ms | 1ms | 5720ms |
| 中继 D=150ms | 303ms | 181ms | 6000ms |
| 中继 D=300ms | 603ms | 348ms | 6150ms |

两个读数都**单调跟随注入的延时** → 公式正确。

**已知不确定度**: 声音那条假定"浏览器的 currentTime=0 就是流的第 0 个采样"。
如果浏览器在起播时丢掉了一小段(实测疑似 ~1s 量级), 读数会**偏大**同样的量。
所以它是"秒级可信、亚秒级别当真"。画面那条没有这个问题。

**收音延时到底有多大 / 能不能优化**(2026-10-23 实测):

- 服务端管道 **0.3s**、网络(本机) **≈0** —— 都不是瓶颈
- **浏览器直播缓冲 ≈5s**, 这才是大头
- 换编码格式只会更差: wav 9.2s / opus-webm 19.4s / aac-adts 19.6s, **mp3 最好(4.6s)**
- "定期把播放头拉到缓冲末端"能压到 ~3.5s, 但会引入可闻的卡顿, 没采用
- 再往下要 MSE / WebRTC —— 而 **iOS Safari 不支持音频 MSE**, 会牺牲 iPhone

## 摄像头画面这条链路(2026-10-23 优化)

`v4l2 -> ffmpeg(解码+按 fps 重编码 MJPEG) -> 管道 -> 服务端分帧 -> WebSocket -> <img>`

三个坑, 都是这次实测出来的(华为 MateBook + SenseTek FHD Camera):

| 坑 | 症状 | 现在怎么做 |
|---|---|---|
| 摄像头**不认 `-framerate`** | 选 5fps 照样吐 28fps; 直出 `-c:v copy` 时连 `-r` 也限不住(裸 mjpeg 封装丢不掉包) | 改成"解码 + 软编", 用**输出** `-r <fps>` 限帧 |
| 直出 MJPEG 每帧 44KB | 640×480@12 实测 **10.1 Mbps**, 选"省流量"也没用 | 软编 `-q:v 5`: 12KB/帧, 相对原图 **PSNR 44.9dB**(看不出), CPU 只多 4.5% |
| `stream.read(65536)` **会阻塞到攒满 64KB** | 12KB 的帧要等 5 帧才处理一次 -> 凭空 +400ms, 帧率还变成"一批一批" | 改用 `read1()`(和音频那条路同一个坑) |

配套还有一条: `pump()` 发送前**把队列里积压的旧帧全丢掉, 只发最新那帧**。
手机网络一慢, 旧帧会在队列和内核发送缓冲区里排队, 画面越看越滞后且永远追不回来;
监控场景下"跳几帧"比"延迟一直涨"可接受。

**别再在服务端按 1/fps 兜底限速**: ffmpeg 丢帧后的输出间隔是 72/108ms 跳着来的
(输入 28fps 的 2 帧或 3 帧), 一刀切在 70.8ms 上会把 72ms 那些也误杀 —— 实测
12fps 掉到 8.2fps。

优化前后(640×480 @12fps, 实测):

| | 帧率 | KB/帧 | 码率 |
|---|---|---|---|
| 优化前 | 27.7 fps(选项无效) | 44.2 | **10.12 Mbps** |
| 优化后 | 11.5 fps(跟选项一致) | 12.4 | **1.17 Mbps** |

各档实测(优化后): 320×240@12 = 1.02 Mbps / 640×480@5 = 0.49 / 640×480@30 = 2.85 /
1280×720@12 = 2.51 Mbps。

**画面延迟的真实构成**(逐段量过): 驱动采集 -> 编码后出管道 **7ms**(中位),
服务端 -> 浏览器 **1~2ms**(局域网)。所以页面上那个"画面 X 前"基本就是全部 ——
剩下的只有摄像头传感器自身和浏览器 JPEG 解码/渲染, 软件量不到。

## ffmpeg 必须**按能力挑**, 不能信 PATH(2026-10-23 大坑)

`~/.local/bin/ffmpeg` 是给 Rerun Viewer 用的 imageio 静态构建(v7.0.2,
johnvansickle), **没有编 pulse 输入设备**, 也不认 `-fragment_size`;
而 systemd 用户环境的 PATH 里 `~/.local/bin` 排在 `/usr/bin` **前面**
(`systemctl --user show-environment` 可以确认)。于是:

| | /usr/bin/ffmpeg (4.4.2) | ~/.local/bin/ffmpeg (静态 7.0.2) |
|---|---|---|
| pulse(收音) | ✓ | **✗** |
| v4l2(摄像头) | ✓ | ✓ |

**症状极有迷惑性: 画面一切正常, 只有收音全废** —— 摄像头页点开麦克风毫无反应,
探测 5 个候选全在 3ms 内失败(`Error splitting the argument list: Option not
found`), 服务端连一个 `/api/audio` 都收不到。更阴的是**在 shell 里手跑 ffmpeg
完全正常**(开发用的 shell PATH 里没有 `~/.local/bin`), 只有服务进程复现。

所以 `server.py` 启动时用 `_pick_ffmpeg()` **显式挑一个同时支持 pulse 和 v4l2
的**: 先 `/usr/bin/ffmpeg`、再 `/usr/local/bin/ffmpeg`、最后才 PATH。挑中的路径
会写进审计日志(`boot ffmpeg -> /usr/bin/ffmpeg (支持: pulse,v4l2)`), 下次一眼
就能看出来。

> 排查提示: `audio_level()` 现在会把 ffmpeg 的最后一行 stderr 带进结果里,
> `GET /api/audio/check?mode=mic` 能直接看到每个候选**为什么**失败 —— 以前
> stderr 被吞掉, 这种情况只能干瞪眼。

## Tailscale 设备列表里的「- # SSH」是什么(2026-10-23 修)

`tailscale status` 的 stdout **末尾会附一段健康检查**, 以 `#` 开头:

```
# Health check:
#     - Tailscale SSH enabled, but access controls don't allow anyone to
#       access this device. Update your tailnet's ACLs at https://...
```

解析器按空白切列取 `ip/host/user/os`, 于是那行被切成
`['#', '-', 'Tailscale', 'SSH', ...]` —— **被当成一台设备**显示了出来:
主机名 `-`、系统 `SSH`、IP `#`, 就是列表最下面那个莫名其妙的条目。

修法两条(双保险):

1. `#` 开头的行直接跳过, 但**内容不丢** —— 去掉 `#` 和列表符号后收进
   `snapshot["ts_health"]`, 由**一键自检**报成「Tailscale 提示」(这段其实有用,
   以前是白丢的);
2. 第一列必须像 IP(`_IPV4_RE`)才认, 免得将来 tailscale 再往 stdout 塞别的段落
   又被当成设备。

## 帧率 / 延时 / 红黄绿(2026-10-23 定稿)

### 两个读数的口径

| | 帧率 | 延时(「xx s 前」) |
|---|---|---|
| 采集模块 | **本机每秒真正收到的帧数**(1 秒窗口, 除以真实经过时间) | 最近一帧**到达时**的年龄 = 本机现在 − 服务端**采出这一帧**的时刻 |
| 远程桌面 | 同上(本地收到的画面帧数) | 最近一帧**到达时**的年龄 = 本机现在 − 服务端**从 x11vnc 收到这块数据**的时刻 |

**时间戳打在"采集"那一端, 不是"发送"那一刻** —— 两者差的是服务端内部排队 +
WebSocket 写阻塞, 机器一忙能有几十毫秒; 那不是网络延时, 不该算进用户看到的数字。
采集模块打在 `_jpeg_frames` 读出管道那一行(`q.put((int(time.time()*1000), f))`),
远程桌面打在 `vnc.recv()` 拿到字节那一行(`recv_at`)。

**到达时刻要单独记**: `/api/time` 的时钟对齐是异步的, 首帧常常在它完成之前就到 ——
那时算不了帧龄。采集模块会一直有新帧所以能自愈, **但桌面静止时不会再来新帧**,
那一栏就会永远停在 `--`(实测踩到过)。所以两边都是「先记 `frameArrivedAt`,
显示时再用 `frameArrivedAt + clockOff - frameSentAt` 算」。

### 显示格式(约定)

**< 1 秒用整数毫秒**(`3ms` / `999ms`), **>= 1 秒用秒**(`1.005s` / `10.12s` / `100.1s`,
秒这一档小数位随量级自适应)。采集模块 / 远程桌面 / 一键自检**三处同一套**。

### 远程桌面只显示「帧率 + 延时」

原来顶栏那个「网络 xx ms」量的是 **HTTP 往返**, 和画面有多旧是两回事(网络很快但
画面卡住完全可能), 用户明确说只关心本地体验, 所以从顶栏**去掉了**; 全屏信息行里
还留着, 需要排查网络时看得到。

### 红黄绿(门槛是拍的, 觉得不合适改这三个函数就行)

| 指标 | 绿 | 黄 | 红 |
|---|---|---|---|
| 画面/桌面延时 | < 0.3 s | < 1 s | >= 1 s |
| 声音延时 | < 2 s | < 6 s | >= 6 s |
| 采集模块帧率 | >= 目标 × 80% | >= 目标 × 50% | < 目标 × 50% |
| 远程桌面帧率 | >= 15 fps | >= 5 fps | < 5 fps |

声音单独一套门槛是因为它天生被浏览器缓冲 ~5 秒(见上一节), 套画面的门槛会永远飘红。
**远程桌面帧率为 0 时不上色** —— 桌面静止时 x11vnc 本来就不发帧, 那不是故障。

### 远程桌面「静止时 0fps」是正常的(实测验证过)

VNC 是**有变化才发帧**的(x11vnc 靠 X DAMAGE / 轮询检测改动区域), 桌面不动就
**一个字节都不发** —— 所以帧率读数是 0。这不是测量错误, 也不是故障:

| 场景 | 测得的本地帧率 |
|---|---|
| 静止桌面 | 0fps |
| 屏幕上放一个 **30fps** 动画窗口(ffplay testsrc) | **26~31fps** |
| 窗口关掉后 | 0fps |

外加一个**绕开 VNC 的独立验证**: 直接 `ffmpeg -f x11grab` 抓 X 屏幕, 隔 3 秒两张图
**0 个像素不同** —— 屏幕确实冻着, 没帧可发。

> 排查提示: 别用"移动鼠标"来制造画面变化 —— **鼠标指针不在 framebuffer 里**,
> 移它根本不会产生更新(我第一次就踩了这个, 只看到 tooltip 那一下冒了 8fps)。

### 画面延时为什么会显示成 `-- 前`(2026-10-23 修)

**症状**: 手机上采集模块的"画面"那一栏一直显示 `-- 前`(本机测试却正常)。

**根因**: `-- 前` 不是"没数据", 而是**算出来是负数**时的显示 ——
`fmtLag()` 判负返回 `--`, 外面又无条件拼了个 `" 前"`。

为什么会负:

```
画面延时 = 本机收到帧的时刻 + 时钟偏移 - 服务端发出帧的时刻
```

- 画面延时本身只有**几毫秒~几十毫秒**
- 而时钟偏移的误差是 **±半个 RTT**(手机上走 Tailscale 就是几十毫秒)
- **两者同一个量级** → 相减经常是负数

声音那条不受影响(它有 5 秒多, 误差淹不掉它) —— 这正好解释了为什么只有画面那条中招。

**修法**:
1. 帧龄**夹到 0 以上**(`Math.max(0, ...)`)。负数不是"没数据", 是"低于测量分辨率",
   显示 `0ms` 才诚实; 真的没数据(`clockOk`/`frameSentAt` 缺)才显示 `--`。
2. 时钟对齐的采样从 3 次提到 6 次(取 RTT 最小的那次, 样本多更容易撞上接近对称的一次)。

> 理论上限: 单向延时小于时钟误差时是测不准的, 所以快网络下这个数就是 `0ms~几ms`。
> 它仍然有用 —— 网络一慢它立刻涨起来。

### 一个既有的无害报错(不是本次引入)

离开 /vnc 时控制台会有一句
`Tried changing state of a disconnected RFB object`。这是 noVNC 内部的 `Log.Error`:
`disconnect()` 之后 WebSocket 的 `onclose` 又触发一次状态切换。用未改动的 HEAD
版本对照过(3/3 一样报), **属于既有行为**, 发生在页面卸载瞬间, 不影响任何功能。

### 往 noVNC 的 RFB 流里插时间戳(有点巧, 记一下)

远程桌面那条 WebSocket 是**原始 RFB 字节流**, 往里塞文本帧会把 noVNC 的协议顶乱。
做法是: 服务端在每块画面前先发一条 `{"t":"f","s":<ms>}` 的**文本**帧, 而
`vnc.js` 里那层 `CountingWS`(它本来就在包 WebSocket 数字节)在 `new NativeWS()`
之后**立刻**注册 message 监听 —— 早于 noVNC 挂自己的处理函数, 事件按注册顺序派发,
所以它 `stopImmediatePropagation()` 之后 **noVNC 一个字节都看不到**。
(实测 noVNC 照常连上、画面正常, 见回归。)

## 远程桌面开声音会被"没人看就停"误杀(2026-10-23 修)

服务端 `/api/audio` 的判据: **开流那一刻如果最近有页面心跳过**(`_page_seen`),
就把这条流绑到那个心跳上, 之后 `CAM_VIEWER_TIMEOUT`(20 秒)收不到心跳就停 ——
本意是"没人听就别占着麦克风"。

采集模块一直在发这个心跳(`/api/audio/hb`), **远程桌面从来不发**。于是:
「刚在采集模块用过麦克风 → 20 秒内切到远程桌面开声音」会被误判成"人走了",
声音播着播着就断(实测播放头走到 ~20 秒处停住)。

修法: `setAudio(true)` 里立刻发一次 `/api/audio/hb`, 之后每 5 秒一次;
关声音时清掉定时器。修完实测: 先开采集模块麦克风 12 秒, 再切远程桌面开声音,
**45 秒连续播放、播放头单调推进到 36.9s、无中断**。

> 这个判据本身是对的(采集模块那边就靠它); 缺的是远程桌面也得"报活"。

另外把**声音延时的"红"门槛从 6s 提到 8s**: 实测就在 5.5~6.1s 之间, 卡在门槛上
会一会儿黄一会儿红(自检里看到过 6.046s 判红)。

## 两个模块的声音源是分开的, 但服务端**同时只跑一路**(2026-10-23 查清)

| 模块 | 声音源 | 采什么 |
|---|---|---|
| 采集模块 `/cam` | `src=mic` | **麦克风**(环境音) |
| 远程桌面 `/vnc` | `src=sys` | **扬声器回环**(电脑正在放的声音) —— 既有功能 |

远程桌面那个声音按钮**不是麦克风回传**, 是 `-f pulse <默认 sink>.monitor`。

**但**: 服务端的音频 hub 是**单音源**的(`_hub["key"] = (src, kind)`,
换源时先 `_hub_stop_locked()` 再起新的)。所以**一边听麦克风、一边听电脑声音是做不到的**
—— 后开的那个会把先开的掐断。实测: mic 流跑着的时候请求 `src=sys`,
mic 那条立刻 `IncompleteRead` 断掉, sys 正常。

这是**既有设计**(`git show HEAD` 里同样有 `_hub_stop_locked()` / `key=(src,kind)`),
不是这次改出来的。实际使用中不容易撞上: 同一个手机上同时只在前台看一个页面,
切后台的那个页面自己会停音频(见 cam.js 的 visibilitychange)。

要支持"两路同时"就得把 hub 改成按 `(src,kind)` 分桶的字典(顺带
`/api/audio/hb` 要带上 src 才能报对应的管道滞后), 代价是两个模块都开时会有
两条 ffmpeg 采集进程。**目前没改** —— 需要的话再说。

## 进页面时的加载进度小框(2026-10-23)

`static/loadtip.js`, 由服务端**统一注入到每个页面的 `</head>` 前**(见 `render()`),
所以以后新加的页面不用手动引。观感沿用远程桌面那个"已按住左键"提示框
(`#pad-mode-toast`): 半透明圆角、白字、`pointer-events:none` 不挡操作。
区别是做成**右上角一个小胶囊**(实测 102×28px), 左边当前步骤、右边百分比,
底边一条 2px 进度; 整句说明和步骤清单放在 `title` 里。到 100% 后**停 1 秒渐隐**。

用法(不调用也有默认行为):

```js
LoadTip.start(['页面', '样式', '建立连接', '首帧画面']);
LoadTip.step('建立连接');
LoadTip.fail('建立连接', '连不上');     // 变红并显示原因
```

各页面的阶段(**都是真实里程碑, 不是编的**):

| 页面 | 阶段 |
|---|---|
| 主页 | 页面 / 样式 / 状态通道(WS 连上) / 首屏数据(第一帧快照渲染) / 曲线(历史图画出) |
| 采集模块 | 页面 / 样式 / 时钟对齐 |
| 远程桌面 | 页面 / 样式 / 建立连接 / 首帧画面(第一帧 FramebufferUpdate) |
| 终端 | 页面 / 样式 / 终端就绪(第一坨输出 = 提示符出来) |
| 其它(日志/主题/背景) | 页面 / 样式(默认) |

`页面` 和 `样式` 由 loadtip.js **自动标完成** —— 页面脚本能跑起来就说明 DOM 好了,
CSS 变量拿得到就说明样式生效了。

### 踩过的两个坑

1. **一开始忘了自动标 `页面`**: 显式 `start()` 的页面进度永远停在 (n-1)/n,
   小框一直挂着不消失(主页卡在 2/3、采集卡在 1/2)。
2. **一开始加了"秒开就不闪"的优化**(100ms 内完成就跳过): 结果采集模块这种
   几十毫秒就加载完的页面**永远看不到提示**(用户反馈"采集模块好像没有")。
   用户要求每次进页面都能看到, 所以改成**立刻出现、每次都显示**。

## 主页信息增强 + 远程桌面指针修复(2026-10-23)

### CPU 卡: 从"看不出来"改成能读出参数

以前只有一个大百分比 + 一排几乎看不见的细条, 用户反馈"啥也看不出来"。现在:

- 标题右边: **CPU 型号**(`Ultra 5 125H`)
- 百分比右边: **线程数 + 大小核划分**(`18 线程 · 8P + 10E`)
- **每核一个格子**: 中间写百分比数字, 底色按负载做**热力图**
  (5%/20%/50% 三档蓝, 80% 以上转黄/红)—— 哪个核在忙一眼就看出来
- 分 **P 核 / E 核**两段画, 各带一行小标题

  > 大小核划分从 `/sys/devices/cpu_core/cpus` 和 `/sys/devices/cpu_atom/cpus` 拿 ——
  > 内核给混合架构(Intel 12 代以后)暴露的分组, 比猜频率上限靠谱。

- **折算占用**: `负载 11.32 / 18 线程 = 63%` —— 光看负载数字没有参照物
- **当前频率**: 平均 MHz / 最高 MHz

### 前台窗口 / 活动(新卡)

- **当前前台是哪个应用**(图标 + 应用名 + 窗口标题 + 窗口 id)
- **上次有人操作是什么时候**

  > 用 **GNOME 的 IdleMonitor**(`org.gnome.Mutter.IdleMonitor.GetIdletime`), 它数的
  > 是"最后一次**键鼠输入**到现在"。所以后台挂着跑代码、放视频**不会**被误判成
  > "有人在用"(用户特别提到这点)—— 那些不产生输入事件。

- **鼠标位置**(屏幕坐标)

### 窗口列表: 图标 + 应用名

以前只有 `0x02200017` + 截断的标题, 看不出是啥应用。现在每行是
`[图标] 应用名 / 窗口标题 / 窗口id`。

**WM_CLASS → 应用名 + 图标**的匹配(`match_app` / `find_icon`):

1. 索引 `/usr/share/applications`、`/var/lib/snapd/desktop/applications`、
   `~/.local/share/applications` 里的 `.desktop`(`StartupWMClass` / 文件名 / `Exec`)
2. WM_CLASS 是 `实例.类` 形式(`Navigator.firefox_firefox`), 先整体匹配, 再逐段
   精确匹配, 最后**只允许后缀**模糊匹配
   > 以前也允许前缀, 结果 `qemu-system-x86_64.Emulator` 里的 "system" 撞上了
   > `system-config-printer`, 把 Android 模拟器显示成"打印机"。
3. 索引**分两遍**建: 先 `StartupWMClass`/文件名(准), 再 `Exec`(次准) —— 否则
   `code-url-handler.desktop`(Exec 也叫 code)会把正牌的 `code.desktop` 挤掉。
4. 找不到就退回首字母角标, 不会空着。

图标走 `GET /api/icon?n=<名字>`:

- 只允许图标目录里的文件(挡住路径穿越)
- **太大先用 ffmpeg 缩到 64px 再发**: `/usr/share/pixmaps` 里有些是 1024x1024 原图
  (chatgpt.png **499KB**、vscode.png 216KB), 而列表里只显示 22px。缩完 4.4KB / 4.9KB。
  > 踩坑: 临时文件不能叫 `.tmp` —— ffmpeg 靠**扩展名**猜输出格式, 会直接
  > "Unable to find a suitable output format" 失败。得叫 `.part.png`。
- 缓存 1 天(图标基本不变)

### 远程桌面: 指针三个问题

| 问题 | 原因 | 修法 |
|---|---|---|
| 进去指针默认在**画面正中** | `virtInit()` 写死 `r.left + r.width/2` | 连上后先拉 `/api/activity` 拿**真实鼠标位置**, 按比例换算; 拿不到才退回居中 |
| 点画面时那个 **○ 不动** | noVNC 把远端鼠标真移过去了, 但虚拟光标 `virt` 没跟着更新 | 在 `#screen` 上监听 pointerdown/pointermove, 同步 `virt` 并重画 ○ |
| 出现一个**很大的鼠标指针** | noVNC 把远端光标图(24x24)原尺寸设成 canvas 的 CSS `cursor`, 但画面是**缩过**的(1440 帧缓冲 → 420 CSS px, 0.29 倍), 光标没跟着缩, 看着比画面大 3 倍多 | `#screen canvas { cursor: none !important }` 藏掉; 位置由 ○ 表示 |

> 位置换算用**比例**而不是坐标: 服务端给 `fx/fy`(0~1), 客户端乘画布宽高 ——
> 这样不用知道 x11vnc 用了什么缩放(`-scale 1/2` 之类)。
> 实测: 把真实鼠标移到屏幕 (2160,480), 进页面后 ○ 落在 (315,277), 理论值也是
> (315,277), **误差 0 像素**。

另外窗口行以前是行内 `<span>`, `text-overflow` 不生效 —— 长标题(比如 VS Code 的
`test_blackbox.cpp (6eb8283) ↔ ...`)会把整页宽度顶开(实测 420px 视口被撑到 730px,
页面能横向滚)。改成 `display:block` 才收住。

## 第二轮: 折叠 / 活动口径 / 电池 / 远程桌面时间戳(2026-10-23 晚)

### 信息面板可折叠, 状态存服务端

每个 `.card` 右上角一个倒三角(▼), 点一下收起、再点展开。折叠 = 只留标题那一行
(CSS `.card.collapsed > *:not(h3) { display: none }`)。

状态存 **config.json 的 `collapsed`**(`{卡片id: true}`), 不是 localStorage ——
和主题色/背景一样属于"这台电脑的偏好", 换台设备打开也一致。

> 踩坑: 批量给卡片插 `data-card` 属性时, 正则的替换串**只返回了 div 标签、没把
> `<h3>` 拼回去**, 结果 12 个卡片的标题全没了, `data-card` 还跑到标签外面变成
> 可见文字。教训: 用正则改 HTML 一定要把**整段**匹配进替换串, 别只替换一部分。

### "上次键鼠操作": 判据与格式

**判据必须是键鼠输入, 不是"页面/窗口有没有变"。** 用户明确要求: 后台挂着 AI
跑任务时页面肯定会变、程序也可能自己弹窗换前台, 那些都不算"有人在用"。

- **Mutter 的 IdleMonitor 在这台机器上是坏的**: 实测连续 12 秒恒为 **64ms** 不动,
  而同一时间 `xinput test-xi2 --root` **一个输入事件都没有**(桌面完全静止)。
- 改用 **X 的 XScreenSaver 扩展**(`xprintidle` 用的就是它), 纯 ctypes 不引依赖。
  实测每秒稳定 +1000ms, 桌面静止时正确累加。
- Mutter 那套留作兜底。

格式: **不写"刚刚"**, 直接给精确时长 —— `7 秒前` / `2 分 16 秒前` /
`1 时 5 分 3 秒前` / `2 天 3 时 20 分前`。卡片底部还有一行小字说明口径。

### 电池: 必须结合"电源插没插"看

内核只报电池自己的状态, 而笔记本在满电附近充电电路会来回切
(充满 → 停充 → 微放 → 再充), `status` 就在 `Full` / `Not charging` /
`Discharging` 之间跳。**光看它会出现"插着电却显示 Discharging"**(用户反馈
"来回切")。实测抓到的正是这个瞬间:

```
BAT0: status=Discharging  capacity=99%      <- 内核这么说
AC0:  online=1                              <- 但电源明明插着
```

所以 `battery()` 顺便读 `/sys/class/power_supply/*/type == "Mains"` 的 `online`,
前端按 (状态 + AC + 电量) 合成文案:

| AC | 状态 | 显示 |
|---|---|---|
| 已接 | charging | 充电中 |
| 已接 | 其他且电量 ≥95% | 已接电源 · 已充满 |
| 已接 | 其他 | 已接电源 · 未充电 |
| 未接 | charging | 充电中 |
| 未接 | 其他 | 用电池(<15% 红, <30% 黄) |

内核原始状态放在 `title` 里, 想看细节仍然看得到。

### 远程桌面的画面时间戳: 改走**旁路通道**

原来把 `{"t":"f","s":...}` 文本帧**塞进 `/ws/vnc`**, 靠 vnc.js 里那层
`CountingWS` 抢在 noVNC 之前注册监听器、再 `stopImmediatePropagation()` 拦掉。
两个问题:

1. **很脆**: 一旦 noVNC 的注册顺序变了, 文本帧就漏进去把 RFB 协议顶乱。
2. **把裸 RFB 客户端打挂了**: `tests/path_check.py` 收到第一帧是
   `{"t": "f", "` 直接报 `不是 RFB 版本`。

现在 `/ws/vnc` 保持**纯 RFB 字节流一个字节都不动**, 时间戳走单独一条
`/ws/vnc-time?viewer=X`(`vnc_time_publish` / `ws_vnc_time`)。谁也不影响。

> 代价是多一条 WS。好处是协议干净、测试全绿。

### 时钟对齐: 6 次 → 3 次且**并发**

`tests/entry_check.py` 盯的是"进远程桌面要快", 其中一个指标是**请求数**。
HEAD 版本正好 15 个(卡在预算上), 加上 loadtip / 时钟对齐 / activity 后到了 23。
收法: 时钟对齐从 6 次降到 3 次, 而且**并发**发(原来是串行 `await`, 3 个往返
叠起来, 手机上白等两个 RTT)。现在 17 个, 预算调到 20 并写明每一笔的用途。

## 第三轮: 折叠三角对齐 / 更新提示(2026-10-23 深夜)

### 折叠三角要"看着"居中, 光把盒子居中不够

两个坑, 都是实测量出来的:

1. **`▼` 这个字符的墨迹不在行的中间**。用 canvas 量: 上伸 **7px**、下伸 **1px** ——
   墨迹几乎全在基线**上方**。盒子居中了, 看上去还是偏上。
   → 改用 **SVG 三角**(`<path d="M0 0h10L5 6z">`), 盒子边界就是墨迹边界, 居中即所见即所得。
2. **折叠时按钮被撑高, SVG 却还贴在顶部**。实测:

   ```
   展开: h3中心=1289.44  按钮中心=1289.44  SVG中心=1289.44   ✓
   折叠: h3中心=1289.44  按钮中心=1289.44  SVG中心=1285.44   ✗ 差 4px
         按钮高 10 -> 18, SVG 没跟着动 -> rotate(-90deg) 后中心就偏了
   ```

   → 折叠键改成**固定 18x18 + flex 居中**, 旋转前后中心一致。实测两种状态都是 **0.00px**。

顺带把**整行标题做成可点**(手机上 18px 的三角太小)。标题里没有别的可点元素, 不会误触。

### "页面已更新"一直消不掉

前端拿 `loadtip.js` **自己** `?v=` 当基准, 而 `/api/version` 给的是**所有资源里最新的**那个
—— 两者只有在 loadtip.js 恰好最新时才相等, 否则**永远不相等, 提示永远消不掉**
(用户: "刷新好几次了还一直提示")。

→ 服务端把真正的版本号**注入页面**(`window.__MEOW_V`), 前端拿它比。实测: 刚打开无提示,
改一次文件弹提示, 点刷新后不再出现。

另外**不做静默自动刷新**: 想过"用户没在看就直接刷新", 但那会打断正在进行的会话
(采集模块在后台收音, 一刷新就断)。宁可让他自己点一下。

### 版本号接口的缓存头

`/api/version` 必须 `no-store`(用户那台网络里有设备会缓存响应)。顺带修了
`_reply()`: `extra` 里的同名头原来是**追加**, 会发出两条 `Cache-Control`(no-cache +
no-store), 语义没准; 改成同名**覆盖**。

## 一键自检(主页多功能面板最下面那个按钮)

点一下把"这台机器现在到底还能不能用"逐项查一遍, 弹窗看结果。分两段:

| 段 | 内容 | 影响 |
|---|---|---|
| `GET /api/selfcheck`(服务端) | ffmpeg 挑的对不对 / 摄像头设备 / PulseAudio 与**麦克风实测** / x11vnc 与 X 显示 / 系统告警(CPU·内存·温度·磁盘·Tailscale) | 只**试采一次麦克风**(0.9 秒), 不碰摄像头 |
| 前端 | 网络往返、时钟对齐、本机 MP3 解码能力、**画面延时**、**声音延时** | 画面/声音那两项要**真采一小段**(摄像头指示灯会亮一下); 声音是**静音播**的(`volume=0`), 不出声 |

`level` 三种: `ok` 正常 / `warn` 能用但要注意 / `bad` 坏了需要处理。
两个延时用的就是摄像头页那套口径(见上), 所以自检报出来的数和页面上看到的一致。

**为什么服务端不查摄像头**: 会亮指示灯、而且是独占设备(和别的页面抢)。
出帧和画面延时交给前端那条测量, 它本来就要采一小段。

**踩过的坑**: 弹窗里那个声音探针必须**在点击的同一个 task 里 `play()`** ——
中间夹了 `await` 之后 `play()` 会被自动播放策略拒掉, 表现是"点了自检但麦克风
那一项永远起不来"(和摄像头页踩的是同一个坑, 见 cam.js 里那段注释)。
