## 2026-09-14 远程桌面四个 bug 的修复

### 运行环境(实测确认, 排查问题时先看这里)

| 项 | 值 |
|---|---|
| 系统 | Ubuntu 22.04.5 LTS (Jammy) |
| 桌面 | **GNOME Shell 42.9, Xorg 会话**(不是 Wayland —— 所以 x11vnc 能抓真实桌面, 且 XTEST 的指针移动 gnome-shell 收得到) |
| Python | **3.10.12**(`/usr/bin/python3`, 服务实际用的; 改动必须过 3.10 编译) |
| x11vnc | 0.9.16 |
| 屏幕 | 2880x1920, GNOME 缩放 1, Dock 在底部 |
| 相关工具 | xdotool 3.20160805.1 / xclip / ImageMagick(import,convert) 都在 |

Dock 相关源码在 `/usr/share/gnome-shell/extensions/ubuntu-dock@ubuntu.com/docking.js`
(GNOME 42 的版本, 前面结论都是照着这份代码 + 真实会话实测得出的)。

### 1) 点一下(触控板/左右键/滚轮键)整个界面卡住, 要再点一次图传才恢复

根因: noVNC 在 `mousedown` 时会调 `setCapture()`, 往 body 插一张覆盖全屏、
`z-index:10000` 的透明层 `#noVNC_mouse_capture_elem`; 它的解除只挂在 **window** 的
`mouseup` 回调里, 而画布自己的 `mouseup` 处理器会先 `stopPropagation()`。
旧实现把触控板手势**合成 DOM MouseEvent 直接派发到 canvas**, 于是 mouseup 永远到不了
window → 遮罩永久留在页面上 → 整个界面被挡住。再点一次图传时那一下落在遮罩上、
冒泡到 window 才把遮罩收掉 —— 这就是"再点一次才不会卡"。

修复: `static/vnc.js` 重写输入层, 不再产生任何 DOM 鼠标事件, 改为**直接调 RFB 协议层**
写指针事件(`RFB.messages.pointerEvent(rfb._sock, x, y, mask)`), 坐标用
`rfb._display.absX/absY` 换算并夹到帧缓冲范围内。不触发 setCapture 就不会有遮罩。
另加 `releaseOverlay()` 看门狗兜底(在事件派发结束后的 `setTimeout(…,0)` 里清理,
不会抢在 noVNC 自己的流程之前把 window 监听摘掉)。

### 2) 滚轮没用 / 没有笔记本触控板手感 / 方向反

旧实现双指要滑 55px 才发 1 档, 而 noVNC 内部 `WHEEL_STEP=50` 又量化一次, 等于没反应,
且没有惯性。现在自己实现累加器 + **抬手惯性**(rAF 衰减), 默认 20px 手指位移 = 1 档,
设置面板可调 0.5x–2.5x; 支持横向滚动; 方向可切("上滑=内容上移 / 上滑=内容下移")。
移动事件按帧合并(一帧最多发一次指针), 顺带省带宽。

### 3) 有点卡 / 有时候直接连不上要刷新

- **x11vnc 去掉了 `-noxdamage`**: 官方文档明确写"用 DAMAGE 扩展能在画面少变时
  *显著降低负载*, 并更快发现小范围变化"。关掉它等于每几毫秒整屏轮询比对。
  实测(临时实例): 静止画面 1.5s 收到 **0 字节**, 指针一动收到 ~11.8KB —— DAMAGE 正常。
- **加了 `-threads`**: 每个客户端一个线程, 一个卡住的客户端不再拖死共享更新循环。
- **桥接加固**: 去掉 `vnc.settimeout(600)`(画面静止时 x11vnc 可以几分钟不发数据,
  原超时会把正常连接判死); 浏览器侧加 90s 读写超时 + 每 20s 一个 WebSocket ping,
  锁屏/切网留下的半死连接会被主动拆掉, 同时 ping 保住 Tailscale 的 NAT 映射。
- **状态面板降载**: `wmctrl`/`tailscale` 都是起子进程的慢字段, 改为 6s/15s TTL 缓存;
  首页和远程桌面页切到后台时主动断开各自的 WebSocket(原来后台标签页还在每 2s
  采一次全量状态, 和图传抢 CPU)。
- **前端自动重连**: 断线后 1s→1.8 倍退避最多 15s 自动重连, 不用再手动刷新。

### 4) Ubuntu Dock 在远程贴到底边不弹出

Ubuntu Dock 有**两套**弹出机制, 由 `require-pressure-to-show` 决定走哪套, 两套都得单独
确认, 否则远程桌面下 Dock 会彻底不弹:

| 设置 | 走的机制 | 远程注入的指针能否触发 |
|---|---|---|
| `true`(Ubuntu 默认) | Mutter **压力屏障**(要求指针"顶住"边缘产生压力事件) | **不能** |
| `false` | **驻留** dwelling(指针停在最后一行像素上保持片刻) | 能 |

实测(`console/tests/dock_ab2.py`, xdotool 注入 vs VNC/RFB 注入 x 两种设置):

    require-pressure-to-show = true   ->  xdotool 无变化 / RFB 无变化
    require-pressure-to-show = false  ->  xdotool 弹出  / RFB 弹出

**所以必须把它设为 `false`**(设置面板里"Dock 贴到底边就弹出"勾上) —— 压力屏障那条路
在远程下是死的, 而它还会同时关掉驻留机制, 等于把 Dock 彻底关死。注意: 沙箱里
`gsettings set` 是静默失败的(能读不能写), 改这个值必须走服务端 `POST /api/dock`。

第二个坑: 驻留判定是**严格相等** `y == monitor.y + monitor.height - 1`
(docking.js 的 `_checkDockDwell`), 而 x11vnc 开了 `-scale 1/2`, 客户端帧缓冲只有一半高:
真实 2880x1920 → 客户端 1440x960, 发客户端最后一行 (x,959) 只能到真实 **1918**,
差 1 像素就永远不弹。

修复(**纯前端, 不用重启服务**):
1. `toFb()` 上限从 `w-1/h-1` 放宽到 `w/h` —— 允许越界一格。实测 x11vnc 在 `-scale` 下
   不先夹客户端坐标, 而是换算后交给 X 夹到屏幕: 客户端 y=960 → 真实 1920 → 夹成 **1919**。
2. **贴边锁(带滞回)**: 指针进入画布边缘 6px 就锁死到最边缘那一行/列, 退回 18px 才解锁。
   为什么需要: GNOME 的 `pointerWatcher` 只在指针位置**变化**时才回调, 而驻留期间任何
   位置变化都会 `_cancelDockDwell()` 取消 —— 手指停在边缘的轻微抖动会不断发出 1918
   把刚建立的驻留打断, 表现就是"得用力顶住才弹"。锁住之后边缘区内一律发最边缘坐标。

端到端验证(`console/tests/dock_latch.py`, 在真实浏览器里拖触控板): 拖到底边 →
真实指针 (1440, **1919**) → **Dock 完整弹出**; 手指回弹 10px → **Dock 保持**; 明确退开
→ 收起。截图 `console/tests/artifacts/dock_latch_result.png`。

设置面板里还有一个"边缘助弹"(`POST /api/edge`, 由服务端用 xdotool 钉住), 保留为
**旧版 x11vnc 的兜底**, 默认关闭。


## 2026-09-14 键盘 / 剪贴板 / 响应速度

### 键盘: 手机上根本发不出的键 + 重复上屏 + 焦点被抢

| 问题 | 原因 | 处理 |
|---|---|---|
| 没有 Ctrl/Alt/Shift | 页面上只有 Ctrl+Alt+Del 一个按钮 | 新增**快捷键条**(工具栏"按键"可收起): 粘滞修饰键 Ctrl/Alt/Shift/Super + Esc/Tab/⏎/⌫/Del + 方向键 + Home/End/PgUp/PgDn + Ctrl+C/V/X/Z/A、Ctrl+Esc、Alt+Tab、Shift+Tab |
| 发不出 Esc/Tab/方向键 | 只有 `keydown` 映射, 手机软键盘没有这些键, 等于完全够不到 | 同上, 全部做成按钮 |
| 输入法重复上屏 | `compositionend` 发过一次后把 `composing` 置回 false, 浏览器紧接着再派发 `input` 时就会再发一遍 | 改成**按事件先后双向拦截**(Chrome 先 compositionend 后 input; Safari 可能相反), 见下 |
| 连打同一个字符被吞 | (我上一版引入的) 按"内容 + 150ms 时间窗"去重, 敲 `-----` 或 `ll` 会丢一半 | 去掉内容去重, 只拦"刚被 compositionend 发过的那一批"; 同一批字符仍然只发一次 |
| 键盘突然没反应 | 输入法组合中途失焦/被系统收起时收不到 `compositionend`, `composing` 永久卡在 true, 之后所有按键都被当"组合中间态"丢掉 | 加 4 秒兜底复位 + `blur` 时复位 |
| 点图传键盘就没了 | noVNC 给 canvas 设了 `tabindex=-1` 并在 `mousedown/touchstart` 上 `focus()` 它, 隐藏输入框失焦、软键盘收起 | `rfb.focusOnClick = false`, 焦点完全由"键盘"按钮掌控 |
| 回车键变成"完成" | `enterkeyhint="done"` 让软键盘回车键只收键盘不产生回车 | 改为 `enterkeyhint="enter"` |

实测: 通过 RFB 连发 **312 个字符**, xev 窗口收到 **312/312 且顺序正确** —— 传输链路
(浏览器→桥接→x11vnc→X)本身**不截断、不丢键**, 所以"长度限制"只可能出在输入法那一层。
超长文本仍然建议走剪贴板(下面那条)。

### 剪贴板: 中文变问号 + 粘贴粘出旧内容

- **中文全变 `?`**: noVNC 的 `clipboardPasteFrom` 普通路径只支持 ISO 8859-1
  (`core/rfb.js` 里写死 `if (code > 0xff) code = 0x3f; // '?'`), 而 x11vnc 0.9.16
  不支持扩展剪贴板协议 —— 走的必然是这条有损路径。**实测: 发 "中文ABC" 到 X 选区,
  读回来是 `??ABC`。** 现在改为服务端用 `xclip` 直接设 X 选区, 与 VNC 协议无关,
  任意 Unicode 都对(实测 25 字中文往返一字不差)。
- **粘贴粘出上一次的内容**: 旧前端先 `rfb.clipboardPasteFrom()` 再立刻 `fetch(/api/paste)`,
  两条路完全异步, Ctrl+V 常在选区还没换过来时就按下去了。现在"设剪贴板 + 按 Ctrl+V"
  由服务端**一次做完**(先 `xclip` 设好并读回确认, 再按键)。
- **只能写不能读**: 新增"读取远端"(`GET /api/clipboard`), 并监听 noVNC 的 `clipboard`
  事件自动同步。
- **终端粘不进去**: xterm 之类不响应 Ctrl+V, 新增"直接键入"(`xdotool type`)。
- 面板改为五个按钮 + 状态回显, 不再点一下就把面板关掉。

### 响应速度: 实测定位

用真实会话量了三段延迟(客户端在回环, 测到的就是服务端管线):

| 环节 | 默认配置 | 说明 |
|---|---|---|
| 指针事件生效 | 25ms | `-nonap -sb 0` 后降到 **9ms** |
| 画面变化→客户端可见 | 4ms | 空闲 65s 后仍然只要 4ms, 说明 `-nap/-sb` **没有**拖慢画面推送 |
| 键盘连发 312 字符 | 312/312 | 不丢键 |

结论: **服务端管线不是瓶颈**(毫秒级)。真正剩下的是网络往返(Tailscale)和手机端解码渲染。
所以这轮改的是能改的部分:

- 去掉 `-noxdamage`(官方文档: 用 DAMAGE 能"显著降低负载"且更快发现小范围变化),
  实测静止画面 1.5s 收到 **0 字节**, 指针一动 ~11.8KB —— 不再整屏空转;
- 加 `-threads`, 单个卡住的客户端不再拖死共享更新循环;
- 桥接层: 去掉 600s 读超时 + 90s 读写超时 + 每 20s WebSocket ping(兼保 NAT 映射);
- 状态面板: `wmctrl`/`tailscale` 子进程改 6s/15s TTL 缓存, 首页与远程桌面页切后台时
  主动断开各自的 WebSocket —— 原来后台标签页还在每 2s 采一次全量状态和图传抢 CPU;
- 前端: 画布矩形做缓存, 不再每帧"读-写-读"交替(`placeCursor` 写样式后立刻
  `getBoundingClientRect` 会强制同步重排);
- 前端自动重连(1s 起, 1.8 倍退避, 上限 15s), 断线不用再手动刷新。

想进一步降延迟可调(改 `meow-vnc.service` 后 restart):

- 画质调"低"会走更强压缩、数据更小, 但 x11vnc 端 CPU 更高; 手机 CPU 弱时反而可能更慢;
- 觉得卡顿而网络好, 可以把 `-scale 1/2` 改成 `-scale 3/4`(清晰度上升、带宽约 2.2 倍);
  注意缩放比例一改, Dock 边缘助弹的比例换算会自动跟着变(服务端按
  `真实尺寸/帧缓冲尺寸` 实时换算, 不用改代码);
- 想牺牲一点省电换输入手感, 加 `-nonap -sb 0`(实测输入延迟 25ms→9ms)。

### 追加修复(第二轮反馈: 输入长度 / 按钮关不掉 / 粘贴乱码 / 手感 / 界面繁杂)

| 问题 | 真因 | 处理 |
|---|---|---|
| "输入长度有限制" | 手机上一个 `<button>` 被点时默认行为会**先把焦点从隐藏输入框挪走** → 软键盘立刻收起。快捷键条上每点一个键(比如方向键)键盘就没了, 得反复点开, 用起来就像"输入被截断" | 全部按钮加 `mousedown` 上 `preventDefault()`(阻止焦点转移, 且不影响 click; 在 `pointerdown` 上拦会把 click 一起吞掉)。现在可以边打字边点快捷键条 |
| "键盘按钮点了关不掉" | 旧逻辑用 `document.activeElement === kb` 判断开关。可点按钮那一刻浏览器已经把焦点挪走了, 于是永远判断成"要打开", 只能开不能关 | 改用显式状态变量 `kbOpen`, 不再看 activeElement |
| 粘贴乱码 / 直接键入不出字 | **`xdotool` 在 C locale 下遇到 UTF-8 会直接报 "Invalid multi-byte sequence encountered", 一个字符都打不出去**; systemd 用户服务不一定继承到 `LANG`。实测: `LC_ALL=C xdotool type 中文` → 0 个 keysym; 换成任何 UTF-8 locale → 正常 | `x_env()` 里检查当前 locale, 不是 UTF-8 就强制 `LC_ALL=C.UTF-8`(不动用户自己的设置) |
| 触控板手感 | 只有线性增益, 只能二选一: 增益低够不到屏幕角落 / 增益高轻轻一碰就飞 | 加**指针加速**(慢速微调用基准增益, 快速甩动最多约 2.9 倍), 档位扩到 低/中/高/极高, 惯性衰减 0.90→0.93 并延长尾程 |
| 界面太繁杂 | 我上一轮又加了一条常驻快捷键条, 变成两条横幅 | 工具栏合成**一条横幅**(键盘 · 按键 · 触控板 · 剪贴板 · 设置); 快捷键条收进"按键"抽屉, **默认收起**; Ctrl+Alt+Del 从工具栏挪进抽屉 |
| 改了后端却没反应 | 前端从磁盘实时读, 刷新即生效; 后端必须重启。旧进程只会静默 404 | 页面加载时探测 `/api/screen`, 404 就在顶部显示横幅: "请执行 systemctl --user restart meow-console meow-vnc" |

### 第三轮: 中文输入丢字(真正的"输入长度有限制") + 双指滚动卡顿

这一轮用**真实浏览器(Firefox/Playwright)+ xev + X 截图**做了端到端验证, 终于把
"输入长度有限制"钉死在具体环节:

**中文输入丢字 —— 根因在 x11vnc, 不在前端。**

实测(打 64 个中文, 在 X 侧用 xev 数):

| 环节 | 结果 |
|---|---|
| 浏览器 `input` 事件 | 64 次 ✓ |
| 前端发出的 RFB keyEvent | 128 条 ✓(每个字符 down+up) |
| **X(xev) 实际收到** | **只有 16 个, 而且 keysym 全乱** |
| 纯 ASCII 对照 | 144/144 全到 ✓ |

原因: x11vnc 收到 Unicode keysym 时必须**临时重映射一个 keycode** 才能落到 X, 连发时
它跟不上就丢/串了 —— 所以中文一打长就"像有长度上限"。

修法: **非 ASCII 不走 RFB 的 keysym 通道**, 改由服务端 `xdotool type`(它自己做重映射
且带间隔)。前端把非 ASCII 攒 80ms 合成一次请求(`POST /api/type`), 请求失败时再退回
原路径兜底。修复后实测: **64 个中文 64/64 全部到达且顺序完全正确**。ASCII 仍走 RFB
(低延迟, 不受影响)。

**双指滚动卡顿 —— 两个真 bug:**

1. 双指时**每根手指各自派发 pointermove, 两根的位移都被累加** → 滚动量翻倍; 而且
   两根手指不可能完全同步, 逐帧差值互相打架 → 一顿一顿。改成**只认第一根手指的位移**。
2. 就地 drain 会在极短时间内灌进几十条小消息(实测一帧最多 36 条), 手机端 WebSocket
   队列反复堆积再清空。改成**每帧合并发送**, 每方向每帧最多 4 档, 累加器封顶 6 档。

另外把贴边改成**滞回锁**(进入 6px 锁死、退回 18px 解锁), 见上面第 4 条: Dock 的弹出
判定要求指针严格等于屏幕最后一行, 手指差一点或抖一下就到不了/被打断。

踩过的坑(别重犯):
- **沙箱里 `gsettings set` 是静默失败的**(`get` 能读到真实值, 写不进去), 会把"设置没变"
  误判成"这个设置没用"。改 dash-to-dock 的设置必须走服务端 `POST /api/dock`。
- 用合成 `PointerEvent` 一次性同步派发整段手势是**不真实的**: `queueMove()` 走
  requestAnimationFrame 节流, 只会发出最后一条, 而且首帧可能还没连上 VNC。要像真手指
  一样**逐条派发并留 ~14ms 间隔**, 否则会得到假失败。
- 判断"Dock 是否弹出"用底部区域截图做像素差时, 底层窗口切换会污染结果(能到 0.8),
  务必同时肉眼看一下图。
- X 侧用 `xev` 当靶子数按键(**发按键前必须先确认 `xdotool getwindowfocus` 拿到的是靶子
  窗口**, 否则按键会打到用户正在用的窗口里); `xev` 的 stdout 要 `stdbuf -o0`。

### 右上角实时延迟(2026-09-14 增)

顶栏右侧一个彩色小胶囊显示当前延迟, 颜色分级: 绿 <80ms / 黄 <200ms / 红 ≥200ms;
点一下立刻重测; 设置面板可关(存 localStorage)。

实现: 每 5s 用 `GET /api/health` 做一次极小请求, 量 HTTP 往返时间, 再取指数平滑
(0.6 旧 + 0.4 新)避免数字乱跳。**为什么不测 VNC 那条 WebSocket**: 它是原始 RFB 字节流,
往里塞自定义消息会污染协议; 而延迟的大头本来就是网络往返, HTTP RTT 完全能代表,
顺带还验证了服务端活着。切后台自动停测, 回前台自动恢复。

判断方法: 延迟常年红色说明是网络(Tailscale 绕行/信号差); 延迟绿色但操作仍卡,
就是手机端解码渲染跟不上, 该去调"画质"或把 `-scale 1/2` 改成更小的比例。

## 安全模型

- **控制台只监听 127.0.0.1**, 外网一律经 `lan_forward.py` 镜像(默认只转控制台端口);
- 转发后的流量仍需过登录: 未登录的页面请求 302 到登录页, 未登录的接口 401/302;
- WebSocket 握手校验 Origin, 跨站网页借浏览器 cookie 连桥(CSWSH)会被 403 拒绝;
- 登录失败 8 次锁 5 分钟; 会话是 HMAC 签名的随机令牌, 90 天滑动过期。

## 2026-09-16 两个"越用越卡"的根因（都在连接生命周期上）

### 1. `lan_forward` 每静默 5 秒掐一次连接（影响最大）

`remote = socket.create_connection((BACKEND, port), timeout=5)` —— 这个 5 秒本意是
**连接**超时，但 `create_connection` 会把它**同时设成 socket 的读写超时**，之后没人清掉。
于是转发泵里 `src.recv()` 每静默 5 秒就抛 timeout，被 `except OSError` 吞掉 →
`finally` 里 `shutdown(SHUT_WR)` → **连接被掐断**。

实测证据：经 `<本机IP>:8390`(走转发器)挂一条空闲的 VNC 桥接，**第 5.0 秒**收到 EOF；
同一时刻经 `127.0.0.1` 挂的能坚持 25 秒以上。

影响面：远程桌面**静止时没有数据**（画面没变化 x11vnc 就不发包）→ 手机端每 5 秒断一次，
表现正是"延迟正常但画面一直重连"；终端挂机、音频静音同理。每次重连又会重建桥接，
把下面第 2 个 bug 的泄漏速度放大 —— 两个 bug 叠加就是"越用越卡"。

修法：`create_connection` 之后补 `remote.settimeout(None)`。
回归：`console/tests/forward_check.py`（自己起一个只绑回环的转发实例，验"空闲 25s 不掉 +
响应头改写没坏"）。

**线上要重启才生效**：`systemctl --user restart dsh-lan-forward`。

### 2. 桥接线程还堵在系统调用里就 `close(fd)` → 幽灵客户端

现象：`ss -tnp | grep 5900` 看得到连接但**属主栏是空的**，`ss -e` 的 cgroup 写着
`meow-console.service`，而控制台自己的登记表（`/api/vnc/clients` 的 `bridges`）是 0。
x11vnc 认为它们还活着；`-shared` 下客户端越多共享更新循环越慢 → 所有人一起卡。

根因：`ws_vnc_bridge` 收尾处 `vnc.close()` 之前**没等搬运线程退出**。线程还堵在
`vnc.recv()`/`sendall()` 里时关 fd，内核会替那个**正在进行的系统调用**继续持有 socket ——
fd 没了、TCP 还是 ESTAB，对端不关就一直挂着。实测每 2~3 次连接漏一个，一晚上攒到 7 个。

修法（三处，见 `server.py::ws_vnc_bridge`）：
- `vnc.settimeout(10)`（原来是 `None`，永久阻塞）
- `v2w` 先 `select(…, 1.0)` 再 `recv`，`stop` 一置位最多 1 秒退出
- 收尾 `join(timeout=3)` 等三个搬运线程退出后再 `vnc.close()`；没退出的记审计

回归：`console/tests/leak_stress.py`（反复连/关，看客户端数会不会累积；修前 5 轮漏 2，修后 30 轮 0）。

**排查手法（可复用）**：判断一条 socket 属于谁，先看 `ss -tnp` 的属主；
**属主为空时看 `ss -e` 的 cgroup 字段** —— 跨 PID 命名空间时 `ss -p` 解析不出 fd，
但 cgroup 仍写着创建它的服务（本次就是靠这个把范围锁到 meow-console 的）。

## 已知边界

- 访问端需要该浏览器的配对 cookie: 换浏览器/清 cookie 后要重新扫码一次
  (面板 mint 新链接即可)。
- 微信内置浏览器对非标准端口明文链接偶尔挑剔:
  优先用系统相机扫码跳转浏览器, 或直接把 /m/ 链接粘进微信收藏再点开。
- 电脑断电/Tailscale 退出 => 自然不可达; 重开后自动恢复。
